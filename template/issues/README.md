# {{projectName}} — Issues

File-based, git-tracked issue management. The filesystem is the database.

## Naming

```
[YYYY-MM-DD]_[STATUS]_[category]_[brief-slug].md
```

Example: `2026-05-02_OPEN_bug_websocket-frequent-reconnects.md`

The first heading inside the file (`# Title here`) is the human-readable title used in the index. Categories and statuses are configured in `config.json`.

## Statuses

| Status | Meaning |
|--------|---------|
| `OPEN` | Reported, not yet started |
| `IN-PROGRESS` | Actively being worked on |
| `TESTING` | Fix applied, under extended validation |
| `RESOLVED` | Fix applied and verified |
| `CLOSED` | Won't fix, duplicate, or no longer relevant |
| `BLOCKED` | Cannot proceed (external dependency, awaiting decision) |

Edit `config.json` to add, remove, or rename statuses. Status order in `config.json` controls section order in `INDEX.md`.

## Workflow

1. **Create** — copy `ISSUE_TEMPLATE.md` to a new file using the naming convention above
2. **Work** — when status changes, **rename the file** (e.g. `git mv ..._OPEN_... ..._IN-PROGRESS_...`). Don't only edit the status field inside the file — the filename is the source of truth
3. **Resolve** — rename to `RESOLVED` (or `CLOSED`) and document the fix in the Resolution section
4. **Re-index** — run `node {{dirName}}/update-index.js` after any create/rename/archive
5. **Archive** — move stale resolved issues to `archive/` periodically (default: 60 days; see `config.json`)

```bash
# Create
cp {{dirName}}/ISSUE_TEMPLATE.md {{dirName}}/$(date +%Y-%m-%d)_OPEN_<category>_<short-slug>.md

# Update status (file rename — preferred via git mv to preserve history)
git mv {{dirName}}/2026-05-02_OPEN_bug_foo.md {{dirName}}/2026-05-02_RESOLVED_bug_foo.md

# Regenerate index
node {{dirName}}/update-index.js
```

## Sprint Workflow (for larger tasks)

If a task is too large for one Claude instance — the build/test/debug loop would consume more than ~60% of the context window — split it into sequential sprints. Each sprint runs in a fresh Claude instance with a clean context.

**Decide at issue-creation time.** Sprint-shaped work needs an execution plan from day one; retrofitting mid-flight loses context. If unsure, err toward fewer sprints with tightly coupled work grouped together.

**Rough sizing:**
- 1 sprint — ~500 lines of changes, one build/test cycle
- 2 sprints — 500-1500 lines, multiple coupled phases
- 3+ sprints — new subsystem, major refactor, independent workstreams

**Each sprint follows 7 steps:**
1. **Read** — issue doc + key files for the sprint's scope
2. **Implement** — code changes for the sprint's layers/phases
3. **Build & Test** — build, deploy, tell the user what to test
4. **Debug** — iterate against logs and user-reported behavior
5. **Document** — update issue Status History, ADRs, architecture notes, CLAUDE.md if patterns changed
6. **Commit** — stage and commit code + docs together
7. **Handoff** — write a single-line prompt the user can paste to start the next sprint's instance

**Issue document additions for sprint work:**

- `## Sprint Execution Plan` — each sprint's scope, key files to read, deliverables, kickoff prompt. Sprint 1's prompt is written during planning; subsequent sprints' prompts are written by the previous sprint's instance.
- `## Status History` — each sprint appends what was actually shipped, deviations from plan, gotchas for the next sprint, and the next handoff prompt.

**Guidelines:**

- Put the riskiest / hardest work in Sprint 1 — debug while context is fresh.
- Keep polish and UI work for later sprints.
- Each sprint must leave the project in a working, testable state.

**Example handoff prompt:**

```
Read {{dirName}}/2026-05-02_IN-PROGRESS_feature_example.md — implement Sprint 2
(layers 4-5: described in the issue's Sprint Execution Plan). Follow the
sprint process in {{dirName}}/README.md. Start by reading all key files listed
under Sprint 2.
```

## Config

`config.json` controls project name, statuses, categories, and how many entries appear in the terminal-status section of the index. Changes take effect on the next `update-index.js` run. The schema:

```json
{
  "projectName": "My Project",
  "statuses": ["OPEN", "IN-PROGRESS", "TESTING", "BLOCKED", "RESOLVED", "CLOSED"],
  "categories": ["feature", "bug", "performance", "infra", "docs"],
  "indexResolvedLimit": 0
}
```

Status order in `statuses` controls section order in `INDEX.md`. `indexResolvedLimit` applies to the **last** status in the list (typically `BLOCKED` or `CLOSED` — whichever you put last); `0` means no limit. Set to e.g. `10` to keep only the most recent 10 entries of that terminal status in the index (older entries still live as files).

For archive workflow, manually move stale issues into `archive/` periodically — there's no script that does it for you.
